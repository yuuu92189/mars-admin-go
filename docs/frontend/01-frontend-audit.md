## Existing Frontend Capability

`frontend-api/` contains only the generated TypeScript contract baseline:

- `frontend-api/src/schema.ts`: generated by `openapi-typescript`.
- `frontend-api/package.json`: pinned `openapi-typescript` and TypeScript.
- No application shell, API client, React components or browser authentication existed before this phase.

The new application therefore consumes the existing generated type file instead of creating a second OpenAPI pipeline.

## Backend Contract Findings

- Canonical auth endpoints are `/api/v1/auth/captcha`, `/api/v1/auth/login`, `/api/v1/auth/me` and `/api/v1/auth/logout`.
- Session cookies are `mars_session`, `mars_refresh` and readable `mars_csrf`; the CSRF header is `X-CSRF-Token`.
- The current source validates the canonical login fields `captchaId` and `captchaCode`.
- `CurrentUser` exposes `user`, `roles`, `permissions` and `menus`; it does not expose `isSuperAdmin`.
- Menu paths from the database are relative, e.g. `system/user`, so the frontend normalizes them to `/system/user`.
- The local Docker service on port 8080 was an older image and rejected canonical captcha fields. Current source was verified separately on port 8081 with the local development database and Redis. This is an environment freshness issue, not a new frontend fallback.

## Gaps and Decisions

| Gap | Decision |
| --- | --- |
| No React application existed | Initialize `frontend/` rather than reuse Vue |
| Superadmin flag not in `CurrentUser` | Do not infer superadmin from a role name; request Dashboard and use backend 403 as the authority |
| Many Vue pages need product-specific APIs | Keep Phase 2 to foundation, login, dashboard and shell; use explicit Phase 3 placeholders |
| Legacy `/api/*` routes existed during the audit | They are now removed; React consumes only canonical `/api/v1` |
| Browser Origin reaches Go directly through rewrite | Use a same-origin Next Route Handler proxy that strips upstream Origin while preserving cookies and CSRF |
