# PostgreSQL Schema

All identifiers are UUIDv7 generated by Go. Timestamps are `TIMESTAMPTZ` and persisted in UTC. The schema is managed only by Goose files in `db/migrations`.

## Identity

- `identity_users`: username/email/phone unique identities, Argon2id hash, status, lock state and TOTP state.
- `identity_sessions`: access/refresh SHA-256 hashes, expiry, revocation and device metadata.
- `identity_one_time_codes`: hashed SMS verification codes.
- `identity_captcha_challenges`: image answer hash and slider position challenge.
- `identity_social_identities`: provider/subject external identity mapping.

## Access

- `access_roles`, `access_permissions`, `access_user_roles`, `access_role_permissions`.
- `access_menus`, `access_role_menus`.
- `access_role_departments` is created after organization tables.

Super administration is `access_roles.is_super_admin`, not a username check.

## Organization

- `organization_departments` uses PostgreSQL `ltree`, not a CSV ancestors string.
- Path updates move descendants in the same transaction.
- Membership, positions and role department scopes use explicit junction tables.

## Business Data

- `storage_*`, `messaging_*`, `notification_*`, `scheduler_*`, `workflow_*`, `codegen_*`.
- Message ordering uses a database identity sequence.
- Client idempotency uses `(sender_id, client_message_id)`.
- Workflow task decisions use row locks and `pending` compare-and-set updates.

## Payments

- `payment_orders` binds provider, merchant order ID, amount, currency and paid state.
- `payment_callbacks` has a unique `(provider, event_id)` constraint and stores accepted/rejected
  outcomes plus payload hashes.
- Provider transaction IDs are unique per provider when present.
- Callback processing is transactional and rejects amount/currency mismatches without changing the
  order's paid state.

## Index Strategy

Indexes are included only for observed access patterns: active sessions, current memberships, unread recipients, pending tasks, message cursors, role scope joins, JSONB workflow document queries and audit time/actor filters.

## Transaction Boundaries

Application services own transactions. No HTTP handler starts SQL transactions. River job insertion
and manual execution history are kept separate where cross-process atomicity is not possible;
business state is always committed first. Payment callback insert, state transition and duplicate
classification share one PostgreSQL transaction.
